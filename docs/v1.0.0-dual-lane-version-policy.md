# v1.0.0 双通道版本策略

> 这是 `v1.0.0` 的历史设计快照。macOS OAuth 可使用系统 Keychain，因此从
> `v2.0.0` 起不再把 profile 文件隔离描述成完整的凭据隔离，而以实际路由、
> endpoint 和监听进程身份作为最终验证。

## 目标

`v1.0.0` 把两个不同目标拆成两个明确入口：

1. 官方 Claude 通道优先控制账号、路由、客户端身份和前台生命周期风险。
2. CC Switch 通道优先获得较新的 Claude Code 工程能力，同时避免把第三方
   compatibility endpoint、token 和 session 带进官方通道。

这不是流量分流器。两个 launcher 都在请求发出前完成本地检查，然后直接执行
经过固定的 Claude Code 二进位。

## 信任边界

### 官方通道

入口：

```text
claude
  -> claude-guard
  -> reviewed Claude Code binary
  -> isolated official profile
  -> HTTP CONNECT proxy
  -> api.anthropic.com
```

安全属性：

- 独立 profile。
- 官方 OAuth 只留在官方 profile。
- 固定客户端版本、SHA-256 和可选 macOS Team ID。
- 检查出口 IP、TLS issuer、HTTP CONNECT 和 IPv6。
- 关闭 background agents、background tasks、cron、Remote Control、hooks、
  workflows 和自动更新。
- 运行中 watchdog 仍为 dry-run，不提供未经验证的自动 pause/kill。

### CC Switch 通道

入口：

```text
claude-cc
  -> CC lane precheck
  -> independently reviewed Claude Code binary
  -> CC Switch profile
  -> local loopback compatibility endpoint
  -> provider selected by CC Switch
```

安全属性：

- 固定独立客户端版本和 SHA-256。
- macOS 可固定 Anthropic Developer ID Team ID。
- base URL 必须与配置中的 loopback endpoint 完全一致。
- endpoint 在启动前必须可达。
- 默认要求 `PROXY_MANAGED` token 模式。
- profile 中存在 `.credentials.json` 时 fail-closed。
- 清除父 shell 继承的官方 route、provider 和 lifecycle 环境变量。
- 关闭 telemetry、OTel exporter、非必要网络流量和自动更新。
- 项目 settings 不得改写 `ANTHROPIC_BASE_URL`、凭据或 provider。
- CLI 不得使用额外 `--settings` / `--setting-sources` 绕过固定 profile。

CC Switch 通道不经过官方 IP/TLS guard，因为 Claude Code 客户端只连接本机
loopback endpoint。上游 provider、出口和服务条款由 CC Switch 配置及其对应
服务负责。

该通道有意保留新版客户端的 background agent、plugin、hook 和其他工程能力。
因此关闭终端后，用户明确启动的后台任务可能继续运行；这属于本机进程和资源
管理边界，不应误解成官方 guard 已经负责暂停或终止它们。

## 为什么是 1.0.0

`0.x` 系列只保护官方入口。`1.0.0` 第一次把双通道作为公开、稳定、可测试的
项目契约：

- 两条通道有不同的配置文件。
- 两条通道有不同的版本更新节奏。
- 两条通道禁止互相继承凭据和路由。
- 安装、回滚和回归测试都进入仓库。

这比单纯把 `claude-cc` 的路径改到一个新二进位有更大的行为边界，因此使用
项目大版本表达。

## 版本矩阵

`v1.0.0` 发布时：

| 角色 | 版本 | 定位 |
| --- | --- | --- |
| 官方通道批准版本 | `2.1.220` | 已完成签章、哈希、入口与 PTY 退出验证 |
| CC Switch 通道批准版本 | `2.1.220` | 发布时 npm `latest`，完成 CC lane 预检 |
| 历史回退基线 | `2.1.170` | 保留原包、二进位、哈希和签章证据 |

版本矩阵是发布时快照。后续更新应创建新版本目录和新配置指针，不覆盖原目录。

## 2.1.170 的历史价值

必须保留 `2.1.170`，原因不是它被认定为永远安全，而是它提供可复现对照：

- 双通道改造前长期使用过。
- 可比较新版 TUI、TLS、resume、plugin、gateway 和 background 行为。
- 新版本回归时可以快速判断问题是否来自客户端。
- 不依赖 npm 当前 `latest` 标签，避免回滚目标漂移。

建议本机保留：

```text
clients/2.1.170/claude
clients/2.1.170/anthropic-ai-claude-code-2.1.170.tgz
```

同时记录：

- `claude --version`
- SHA-256
- npm integrity / shasum
- macOS `codesign` 和 Team ID

不要把大型二进位或私有配置提交到本仓库。

## 模型大版本与客户端大版本

模型和客户端应分开决策：

1. 新模型发布后，先确认对应服务端或网关是否真的开放。
2. 再确认模型名称或 alias 如何映射。
3. 只有新模型依赖新客户端能力时，才升级客户端。
4. 升级客户端必须独立做版本、哈希、签章、route 和 lifecycle 回归。
5. 不使用真实 prompt 作为安装验收；先完成无模型请求检查。

客户端选择器里出现模型不等于服务端已授权；客户端没有显示模型也不一定代表
服务端完全不可用。Guard 不伪造模型列表，也不重写 model ID。

## 升级流程

### CC Switch 通道

1. 查询官方发布页和 npm `latest`。
2. 下载到新的版本目录，不覆盖当前版本。
3. 核对版本、SHA-256、npm integrity 和 macOS 签章。
4. 更新 `~/.safe-claude-cc.json` 的固定路径和身份字段。
5. 执行 `claude-cc --precheck-only`。
6. 执行 `claude-cc --version`，确认新客户端。
7. 在不提交 prompt 的情况下观察客户端只连接本机 CC Switch endpoint。
8. 保留旧版本至少一个观察周期。

### 官方通道

官方通道不自动跟随 `latest`。除了上述验包，还必须重新运行：

```bash
./scripts/check.sh
python3 scripts/verify-terminal-exit.py
claude-guard --precheck-only
```

确认 PTY 关闭后没有 supervisor、worker 或同进程组 sidecar 残留，才允许修改
官方固定指针。

## 回滚

CC Switch 通道回滚只修改 `~/.safe-claude-cc.json` 的：

- `command`
- `client_version`
- `client_sha256`
- `client_macos_team_id`

然后再次运行 `claude-cc --precheck-only`。不要删除新版本，直到问题被定位。

官方通道和 CC Switch 通道的回滚互不影响。任何回滚都不应复制 credentials、
session 或 settings 到另一条通道。

## 政策边界

本项目不：

- 提取或转发 Anthropic OAuth token。
- 把官方订阅凭据交给 CC Switch。
- 修改发往服务端的请求正文或归因字段。
- 伪装 timezone、locale、设备或客户端身份。
- 绕过账号限制、封禁或服务保护措施。

`claude-cc` 是用户管理的第三方兼容链路，不应被描述成 Anthropic 官方支持的
模型通道。使用者仍需遵守所连接 provider、网关和客户端软件的适用条款。

## 验收标准

发布前必须全部满足：

- `./scripts/check.sh` 通过。
- 官方 PTY close 实机测试通过。
- `claude-cc --precheck-only` 通过。
- 两条入口解析到预期 launcher。
- 两条配置固定不同 profile。
- CC profile 不存在官方 credentials。
- 官方 profile 不存在 CC Switch base URL/token。
- CC endpoint 只监听 loopback。
- 旧版本二进位与原包仍可读取和校验。
- GitHub `main`、tag 和 CI 指向同一提交。
