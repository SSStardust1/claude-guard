# Claude 守护 v0.2.0 技术评估说明

更新时间：2026-07-01 10:55 +08

仓库：`https://github.com/guiltyluce/claude-guard`

当前分支：`codex/claude-session-guardian-v0.2.0`

当前版本：`0.2.0`

当前提交：`a1d0a67 feat: add claude session guardian v0.2.0`

## 评估结论

`v0.2.0` 适合作为一个 dry-run 观察版合并到 `main`，但不应被描述为已经具备“运行中自动暂停/恢复/kill Claude Code”的完整守护能力。

从安全风险看，本版本默认不读取 Claude OAuth token，不发送模型请求，不改写 Claude API base URL，不接触 `127.0.0.1:15721` 旧反代链路，不会把订阅 OAuth token 托管给第三方。因此作为官方 Claude Code 启动前门禁和运行中低频观察器，账号侧风险较低。

从运行稳定性看，本版本默认只做启动前检查和运行中 dry-run 日志记录，不会给 Claude 进程发送 `STOP`、`CONT` 或 `KILL` 信号，也不会修改 Clash/Mihomo/系统代理配置。因此合并本身对现有 Claude Code 工作流影响较低。真正的限制是：网络波动发生在 Claude Code 已经运行后，本版本只能记录“本来会暂停/恢复”，不能实际阻止正在进行的 Claude 请求继续重试。

推荐结论：

- 可以合并：作为 `v0.2.0 dry-run guardian`。
- 可以试运行：用 `claude-guard` 显式启动几次观察日志。
- 不建议立刻宣称：已经具备完整 fail-closed 运行时保护。
- 不建议立刻替换所有 `claude` 入口：除非先接受 dry-run 边界，并观察日志确认没有误判。

## 当前版本目标

这个项目的目标是给官方 Claude Code CLI 增加一个本地安全入口，避免以下事故：

- 代理没开或出口 IP 漂移时误启动官方 Claude Code。
- TUN/代理配置异常导致请求走到非预期出口。
- TLS 被 Charles、mitmproxy、Fiddler、ZScaler 等中间人证书改写。
- 旧 CC Switch / 反代配置残留在官方 profile 中。
- `ANTHROPIC_BASE_URL`、`ANTHROPIC_AUTH_TOKEN`、`apiKeyHelper` 等高风险配置污染官方链路。
- `fable5` 这类不存在或不安全的模型别名被误传给官方 CLI。

`v0.2.0` 在 `v0.1.0` 启动前门禁基础上增加了运行中 dry-run guardian。它会低频检测 IP 和官方 API 路径，并记录本来应该采取的 pause/resume 决策。

## 运行架构

当前入口文件是：

```text
bin/claude-guard
```

默认配置文件是：

```text
~/.safe-claude-official.json
```

配置文件示例：

```json
{
  "command": "/usr/local/bin/claude",
  "allowed_ips": ["203.0.113.10"],
  "allowed_cidrs": ["203.0.113.0/24"]
}
```

其中 `command` 必须是原始 Claude CLI 的绝对路径，不能写成 `claude`，也不能指向 `claude-guard` 自己。这个设计用于避免 wrapper 递归调用。

默认官方 settings 文件是：

```text
~/.claude-official/settings.json
```

启动 Claude 时，脚本使用 `env -i` 构造干净环境，并显式注入：

- `CLAUDE_CONFIG_DIR=$HOME/.claude-official`
- `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY=http://127.0.0.1:7897`
- `NO_PROXY=127.0.0.1,localhost,::1,.local`
- `DISABLE_TELEMETRY=1`
- `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`
- `CLAUDE_CODE_CERT_STORE=system`
- `SSL_CERT_FILE=/etc/ssl/cert.pem`
- `NODE_EXTRA_CA_CERTS=/etc/ssl/cert.pem`

最后执行：

```bash
"$CLAUDE_BIN" --setting-sources= --settings "$OFFICIAL_SETTINGS" "$@"
```

这个设计的安全含义是：官方 Claude Code 使用独立 profile，且不从当前 shell 继承 `ANTHROPIC_*`、`CLAUDE_*`、旧代理、旧 base URL 等环境残留。

## 启动前检查

启动前检查是硬门禁，失败时默认不启动 Claude。

### 1. 配置文件检查

检查 `~/.safe-claude-official.json` 是否存在，且 `command` 是可执行的绝对路径。

安全价值：

- 避免误调用 wrapper 自己。
- 避免 `PATH` 顺序变化导致实际运行到错误的 `claude`。

### 2. 官方 settings 残留检查

扫描 `~/.claude-official/settings.json`，如果命中以下内容则拒绝启动：

```text
ANTHROPIC_BASE_URL
ANTHROPIC_AUTH_TOKEN
ANTHROPIC_API_KEY
apiKeyHelper
127.0.0.1:15721
PROXY_MANAGED
```

安全价值：

- 防止官方链路回流到旧 CC Switch / 反代。
- 防止 OAuth token 或 API key 注入。
- 防止第三方 helper 接管凭据。

### 3. 出口 IP 白名单检查

通过配置的代理请求：

```bash
curl -4 -x "$CLAUDE_GUARD_PROXY" https://ipinfo.io/ip
```

默认 IP 查询源是：

```text
https://ipinfo.io/ip
https://api.ipify.org
```

如果第一个源不可达或返回无效 IPv4，会自动尝试下一个源。可通过 `CLAUDE_GUARD_IP_CHECK_URLS` 覆盖。

如果当前出口 IP 不在 `allowed_ips` 或 `allowed_cidrs` 中，默认退出。用户必须手动输入 `unsafe` 才能继续。

安全价值：

- 防止代理没开、节点漂移、TUN 掉线后误启动。
- 防止 coffee shop / 公司网络 / 家庭直连等非预期出口误触发官方 Claude Code。
- 避免 `ipinfo.io` 短时不可达导致单点误伤。

### 4. 官方 API TLS / CONNECT 检查

检查 `api.anthropic.com` 是否满足：

- 使用 IPv4。
- 通过 `http://127.0.0.1:7897` HTTP CONNECT 隧道。
- TLS 验证通过。
- 证书 issuer 不像 Charles、mitmproxy、Fiddler、ZScaler、Clash、Surge 或通用 proxy/MITM。

`platform.claude.com` 也会检查，但默认是 warn 模式。

安全价值：

- 确认是官方端点。
- 确认代理只做 CONNECT 字节转发，不做 TLS 解包。
- 发现证书异常时拒绝启动。

### 5. IPv6 泄漏检查

脚本会尝试 `curl -6 https://api.anthropic.com/`。如果可以通过公网 IPv6 访问，则拒绝启动。

但 Mihomo/Clash fake-ip 返回的 IPv4-mapped 地址不会被误判为公网 IPv6，例如：

```text
::ffff:198.18.0.15
```

安全价值：

- 防止 Claude Code 走 IPv6 直连绕过固定 IPv4 出口。
- 兼容 Clash/Mihomo fake-ip 场景，减少误报。

### 6. 模型别名检查

如果参数中出现以下模型名，直接拒绝：

```text
fable5
claude-fable5
claude-fable-5-latest
```

安全价值：

- 防止把非官方或不存在模型名传入官方 CLI。
- 避免因模型错误导致异常重试或误判链路。

## 运行中 dry-run guardian

`v0.2.0` 默认启用运行中观察：

```text
CLAUDE_GUARD_WATCHDOG=1
CLAUDE_GUARD_WATCHDOG_DRY_RUN=1
```

默认检查频率：

```text
IP 检查：60 秒
API 路径检查：180 秒
tick：5 秒
sleep/wake gap：120 秒
IP bad threshold：2 次
API bad threshold：3 次
resume good threshold：2 次
```

运行中 guardian 会记录以下状态：

```text
healthy -> degraded -> paused -> resume-pending -> healthy
```

但在 dry-run 模式下，`paused` 只是内部状态和日志，不会真的暂停 Claude。

日志路径：

```text
~/.claude-guard/guard.log
```

dry-run 的 pause/resume 提示默认只写日志，不向 Claude Code 的 TUI stderr 打印，也不弹 macOS 通知。需要显式提示时可设置：

```bash
CLAUDE_GUARD_DRY_RUN_STDERR=1
CLAUDE_GUARD_NOTIFY=1
```

日志只包含时间、状态、当前 IP、代理路径、动作原因等诊断信息，不包含 OAuth token、API key、prompt、模型响应或 credentials 内容。

## 明确没有实现的能力

本版本没有实现以下能力：

- 不会真正暂停 Claude Code。
- 不会真正恢复 Claude Code。
- 不会 kill Claude Code。
- 不会自动重启 Claude Code。
- 不会修改 Clash/Mihomo/Hiddify/系统代理配置。
- 不会让不稳定网络变稳定。
- 不保证正在 streaming 的 API 请求在网络波动后还能无损恢复。

如果设置：

```bash
CLAUDE_GUARD_WATCHDOG_DRY_RUN=0
```

当前版本会直接拒绝 action mode 并退出，而不是启动一个不安全的半成品暂停逻辑。

这是一个保守但正确的安全选择：Claude Code 可能会派生 `git`、`npm`、`curl`、测试进程等子进程。只暂停 Claude 主 PID 不够安全，必须能暂停整个进程组。当前前台 TUI launcher 尚未实现可靠的 process-group runner，因此不启用真实暂停。

## 安全风险评估

### 低风险项

- 不读取 Claude OAuth token。
- 不读取 `.credentials.json`。
- 不发送模型请求。
- 不消耗 Claude 额度。
- 不修改 Claude 官方账号状态。
- 不修改系统代理。
- 不修改 Clash/Mihomo 配置。
- 不默认替换现有 `claude` 命令。
- 不接触旧 `127.0.0.1:15721` 反代链路。
- 默认 action mode 被禁用，不会误杀或误暂停进程。

### 中等风险项

- 如果用户主动把 `claude-guard` 设为主 `claude` 入口，启动前检查会增加几秒等待时间。
- 如果用户显式设置 `CLAUDE_GUARD_DRY_RUN_STDERR=1`，dry-run guardian 可能在 Claude TUI 运行时向 stderr 打印提示，极端情况下会影响终端观感。
- 运行中检查依赖外部 IPv4 echo 服务和 `api.anthropic.com` HEAD/TLS 探测；如果这些探测短时波动，日志可能记录 false positive。
- `allowed_ips` / `allowed_cidrs` 是静态白名单。如果固定节点更换到白名单外 IP，必须更新配置，否则会阻止启动。
- 数据中心 IP 信誉风险不由本项目解决。本项目只能确保使用固定出口和官方链路，不能把 VPS/DC IP 变成住宅 IP。

### 高风险项

当前默认配置下没有发现高风险项。

如果未来启用真实 pause/resume，需要重新评估：

- 是否能暂停整个 Claude 进程组。
- Ctrl+C、stdin/stdout/stderr、TUI、子进程退出码是否正确。
- sleep/wake 后是否会误 resume。
- 进程残留是否可控。

## 运行稳定性评估

合并到仓库层面：低风险。

安装但不替换 `claude`：低风险。

把 `claude-guard` 作为显式入口试跑：低到中风险，主要风险是探测误判，而不是 Claude 请求风险。默认 dry-run 不刷 TUI、不弹通知。

直接替换所有 `claude` 入口：中风险，因为它会改变日常启动路径。建议先试跑 2 到 3 个真实会话，观察 `~/.claude-guard/guard.log`，再决定是否替换主入口。

稳定性边界：

- 启动前：可以有效 fail-closed。
- 运行中：只能 observe，不能 fail-closed。
- 网络异常：会记录 would-pause，但 Claude Code 自身仍可能继续 retry。
- sleep/wake：会检测长 tick gap 并强制重新验证，但 dry-run 不会实际挡住 Claude。

## 与早期设计文档的差异

早期设计文档中提到 `v0.2.0` 目标包括 process-group pause/resume。当前实现没有启用这个能力，而是做了更保守的修正：

- dry-run 观察落地。
- action mode 被显式拒绝。
- 真实 process-group runner 延后到下一版本。

这个差异不是安全退步，而是安全收敛：在无法证明 process-group/TUI 行为可靠之前，不给用户“已经能安全暂停”的错觉。

评审时建议重点确认：README、CHANGELOG 和本说明文档是否已经把这个边界讲清楚，避免使用者误解。

## 合并建议

建议合并，条件如下：

1. 合并说明中明确写 `v0.2.0` 是 dry-run guardian，不是真实 action guardian。
2. 合并后可以打 `v0.2.0` tag，但 release note 要强调“不发送信号、不暂停、不 kill”。
3. 暂不自动替换用户当前 `~/.local/bin/claude` 主入口。
4. 如要安装试运行，先使用：

```bash
./scripts/install.sh
~/.local/bin/claude-guard --precheck-only
```

5. 真实会话试跑时保留默认 dry-run：

```bash
CLAUDE_GUARD_WATCHDOG_DRY_RUN=1 claude-guard
```

6. 观察日志：

```bash
tail -f ~/.claude-guard/guard.log
```

## 下一版本建议

下一版如果要实现真正运行中保护，应优先做以下内容：

- 用 process-group runner 替代当前 foreground `exec` 模式。
- 确保 Claude 主进程和子进程一起 pause/resume。
- 确保 Ctrl+C、终端尺寸、stdin/stdout/stderr、退出码正确透传。
- 增加 fake Claude 进程组集成测试。
- 增加 sleep/wake 后的恢复测试。
- 再考虑是否提供自动 kill，并且默认仍应关闭。

在 process-group runner 通过验证前，不建议开启真实 pause/resume 或 kill。
